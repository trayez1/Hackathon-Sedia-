# Deploying okayUway to Render

This repo includes a `render.yaml` Blueprint that deploys two services:

- **`okayuway-backend`** — the Node/Express + SQLite API (`backend/`), as a Web Service
- **`okayuway-frontend`** — the Vite/React app, as a Static Site

## 0. Push this repo to GitHub (or GitLab/Bitbucket)

Render Blueprints deploy from a git repo — create a repo and push this project there first.

## 1. Create the Blueprint on Render

1. Go to https://dashboard.render.com → **New** → **Blueprint**
2. Connect the repo you just pushed
3. Render reads `render.yaml` at the repo root and shows you the two services it's about
   to create — confirm and click **Apply**

## 2. Set the two secret env vars

`render.yaml` deliberately leaves the admin passwords out of the file (`sync: false`) so
they're never committed to git. Before or right after the first deploy, go to the
**okayuway-backend** service → **Environment** and set:

```
ADMIN1_PASSWORD = <choose a real password for Adib>
ADMIN2_PASSWORD = <choose a real password for Aniq>
```

`JWT_SECRET` is auto-generated by Render (`generateValue: true`) — you don't need to touch it.

## 3. Wait for both services to deploy

- The backend build runs `npm install` then `npm start` (`node server.js`), and needs to
  pass its health check at `/api/health` before Render marks it live.
- The frontend build runs `npm install && npm run build` and publishes the `dist/` folder
  to Render's CDN.

## 4. Double-check the service URLs match

`render.yaml` assumes your services end up at:

- `https://okayuway-backend.onrender.com`
- `https://okayuway-frontend.onrender.com`

Render normally gives a service exactly this URL (based on the `name` in render.yaml), but
if either name was already taken, Render will have appended a random suffix instead. Check
the actual URLs shown in the Render dashboard for both services, and if they differ from
the above:

- Update `CORS_ORIGIN` on **okayuway-backend** to the real frontend URL
- Update `VITE_API_BASE_URL` on **okayuway-frontend** to the real backend URL
- Redeploy both (a plain env var change triggers a redeploy automatically)

## 5. Visit the site

Open the frontend URL — that's your live app. Sign in at `/admin` with the email/password
you set in step 2.

## Important: the persistent disk (SQLite) requires a paid plan

SQLite is a single file on disk. Render's **free** web service plan has no persistent
disk — the filesystem resets on every deploy and periodically on restarts, which would
wipe your database and uploaded photos/ID documents.

`render.yaml` sets `plan: starter` on the backend and attaches a 1 GB disk mounted at
`/data`, with `DB_PATH`, `UPLOADS_DIR`, and `SECURE_UPLOADS_DIR` all pointed at that disk
so data survives deploys and restarts. If you want to stay on the free plan instead:

- Remove the `disk:` block and the `plan: starter` line from `render.yaml`
- Understand that the database, uploaded obstacle photos, and identity-verification
  documents will all be wiped on every deploy/restart — fine for a quick demo, not for
  anything real
- For anything beyond a demo, moving from SQLite to Render Postgres (a proper managed
  database) is the more durable option long-term, though that's a bigger code change than
  this Blueprint makes

## Everyday workflow after the first deploy

- Push to your connected branch → Render auto-redeploys both services
- To reset the demo data on the live site, you can still hit the existing
  `POST /api/admin/reset` endpoint (requires an admin JWT) — it does **not** touch the
  files on the persistent disk from old uploads, so combine it with the existing
  `POST /api/admin/verification/cleanup` endpoint if you also want old identity documents
  purged.
